# AI Search history and seven-day interpretation cache

Status: implemented and verified locally; not deployed. Production remains build osm4NYyfTiOr7rQigfiga. No API spend, production data changes, toggle changes or Git push.

- History + clock beside AI Search opens private seven-day successful-search history. Entries retain query, selected other-user IDs and last-used timestamp; identical query/group entries deduplicate. Replay goes through normal permission, people visibility, availability and watched-status checks. History is lazy-fetched only when opened and keyed by authenticated user in the client; endpoint never accepts another user's ID.
- Interpretation cache now persists under the configured data volume's ai-search/<userId>.json, with a seven-day lifetime from generation. Cache keys include model, complete developer prompt and cleaned query. A group change reuses interpretation but reapplies current group exclusions. Prompt/model changes invalidate old interpretations. Concurrent identical requests share one provider call.
- Per-user asynchronous serialized operations and atomic file replacement avoid catalogue SQLite writes and lost updates. Files are created with mode0600 where supported. Expired entries are inaccessible and pruned on subsequent access; inactive users' expired bytes can remain on disk until access. No claim of automatic erasure from backups.
- Browser sessionStorage keeps the screen snapshot and draft per account for Back/reload, without another model call. Snapshot is a navigation convenience, not freshly verified results; explicitly searching or replaying history rechecks current catalogue state. Browser storage failure does not disable searching. Server history/cache survive app restarts; browser snapshots last only for that tab/session and expire after seven days.
- No Letterboxd score filtering added. Cache-first filtering would be fast with incomplete score coverage; uncached score retrieval should be an explicit bounded operation rather than silently blocking normal search.
